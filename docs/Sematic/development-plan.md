# OpenClaw-RVGuarder 开发计划

## 1. 文档目标

本计划面向当前项目的最终定位：作为 OpenClaw 的本地安全插件，围绕邮件收发、日报生成与外发、个人办公自动化等高频场景提供可审计、可审批、可运行时验证的安全防护能力。

本计划同时兼顾两个目标：

- 保障项目长期可维护、可扩展、可验证
- 让开发初学者能够以渐进方式学习并完成真实交付

## 2. 开发原则

- 场景优先：先覆盖高频真实办公场景，不追求抽象能力先行
- 主链优先：优先改造当前真实运行主链，不先做大规模重构
- 安全优先：任何自动化执行能力都必须与审批、审计、约束保真联动
- 低复杂度优先：优先选择易学、易测、易部署的技术方案
- 分阶段验收：每阶段都要有可运行产物和明确验收标准
- 接口优先：语义层直接产出 `rv_trace` 给 RV 层消费，不额外增加独立中间层模块

## 4. 阶段 0：学习融入阶段

### 4.1 阶段目标

- 读懂当前项目真实主链
- 明确哪些代码已经稳定、哪些代码存在历史遗留痕迹
- 建立对“规则层、语义层、审批层、审计层、RV 层”的基本理解

### 4.2 学习内容

- 当前主链：
  - `openclaw_guard/conversation.py`
  - `openclaw_guard/manager.py`
  - `openclaw_guard/integrations/detection.py`
  - `openclaw_guard/integrations/control.py`
  - `openclaw_guard/integrations/tool_hook_bridge.py`
- 核心概念：
  - `BehaviorEvent`
  - `DetectionDecision`
  - `ControlledAction`
  - `trace`
  - `rv_trace`
  - `ask / block / escalate`

### 4.3 交付节点

- 一份主链说明笔记
- 一份场景术语表
- 一份当前能力与缺口清单
- 能手动解释“一个工具调用如何被拦截、审批、审计”

### 4.4 验收标准

- 能独立说明当前聊天侧与 Hook 侧的处理差异
- 能指出当前关键词匹配方案的 3 个以上局限
- 能跑通现有项目基础命令与界面
- 能用自己的话解释为什么语义层必须服务 RV

### 4.5 对初学者的要求控制

- 不要求此阶段理解完整时序逻辑
- 不要求掌握复杂形式化工具
- 重点放在读懂现有代码和跑通已有链路

## 5. 阶段 1：语义层最小落地 ✅ 已完成

### 5.1 阶段目标

- 在不破坏当前主链的情况下，引入结构化语义增强
- 为后续 RV 产出稳定的输入格式

### 5.2 已完成任务

- 新增 `openclaw_guard/integrations/semantic_enhancer.py` — 独立 `SemanticEnhancer` 类，支持 LLM API（DeepSeek Chat）与本地规则化降级回退双模式
- API key 通过环境变量 `DEEPSEEK_API_KEY` 或构造函数注入，不写死
- LLM 调用失败/超时/返回非 JSON 时自动降级到本地规则化实现
- 语义标签体系覆盖 7 个维度（基础、命令、路径、网络、配置、渠道/技能、办公场景）
- 在 `manager._annotate_event_context()` 统一接入所有入口
- 语义结果写入 `event.metadata["semantic"]` 和 `event.metadata["rv_trace"]`
- `DetectionEngine.evaluate()` 重构为语义优先决策模式
- 47 条规则匹配输入从原始字符串切换为语义标签
- 新增 5 条办公场景策略（`_office_decision()`）：邮件外发阻断、日报外发阻断、群发升级、AI草拟审批、日报范围确认
- `rv_trace` 作为语义层直接产出，不设独立中间层
- 打包配置从静态列表改为自动发现子包

### 5.3 已覆盖场景

- 邮件发送 (`mail_send`)
- 邮件读取 (`mail_read`)
- 日报生成 (`report_generate`)
- 日报外发 (`report_send`)
- 附件下载 (`attachment_download`)

### 5.4 已交付

- 可运行的 `SemanticEnhancer`（本地规则化实现，延迟 < 1ms）
- 语义标签体系共 7 个维度，覆盖命令、路径、网络、配置、渠道/技能、办公场景
- 实际产出格式包含 `semantic`（含 `scenario`、`labels`、`confidence`、`constraints`）与 `rv_trace`
- 测试文件 `tests/test_semantic_enhancer.py`，覆盖语义增强器输出、manager 入口语义标注、办公场景决策

## 6. 阶段 2：核心场景安全功能开发 🚧

### 当前状态

办公场景标签与策略已在阶段 1 中提前实现：

- 5 种办公场景已可识别：`mail_send`、`mail_read`、`report_send`、`report_generate`、`attachment_download`
- 5 条办公场景策略已直接参与决策（`_office_decision()`）
- 办公原子命题标签已覆盖：`external_recipient`、`bulk_send`、`contains_attachment`、`contains_secret`、`ai_generated_content`、`internal_source`、`missing_scope_constraint`

剩余工作集中在方面：

### 6.1 阶段目标

- 让项目真正具备"办公安全插件"能力，而不只是通用动作拦截

### 6.2 子阶段 A：邮件场景

#### 重点能力

- 邮件读取与线程理解
- 邮件草拟与发送前审批
- 外部域名识别
- 附件与敏感内容联动检测

#### 重点规则

- 外部域名外发拦截
- 群发升级审批
- AI 自动生成内容未确认禁止直接发送
- 附件中含敏感内容时禁止自动转发

#### 邮件阶段交付节点

- `mail_read / mail_draft / mail_send` 场景标签
- 邮件场景规则集
- 邮件场景 RV 模板

#### 邮件阶段验收标准

- 能正确区分草拟与发送
- 能识别外部收件人和内部收件人
- 能对含敏感内容的邮件执行 `ask` 或 `block`

### 6.3 子阶段 B：日报/简报场景

#### 日报阶段重点能力

- 多源汇总
- 摘要来源标注
- 外发前范围确认
- 敏感信息二次检查

#### 日报阶段重点规则

- 来源越权时阻断
- 对外日报默认严格审批
- 内部系统信息未脱敏时禁止外发

#### 日报阶段交付节点

- `report_generate / report_send` 场景标签
- 多源摘要 provenance 标记
- 日报外发规则与 RV 监视模板

#### 日报阶段验收标准

- 日报场景能输出来源列表
- 外发前能检查接收对象和摘要内容
- 高风险摘要外发路径可进入审批或阻断

## 7. 阶段 3：性能与安全测试

### 7.1 阶段目标

- 验证项目在办公高频场景下是否具备稳定、低时延、低误判的安全防护能力

### 7.2 测试范围

- 规则链延迟
- 语义增强延迟
- RV 在线检查延迟
- 审计链完整性
- 场景误报/漏报
- 回退路径稳定性

### 7.3 重点测试项

- LLM 超时是否安全回退
- 结构化解析失败是否保守处理
- 邮件外发是否存在漏拦截
- 日报外发是否存在未脱敏内容放行
- 连续多步动作下的 RV 是否稳定工作

### 7.4 交付节点

- 性能测试报告
- 安全测试清单
- 场景误报漏报分析表
- 最小压测脚本或测试样例集

### 7.5 验收标准

- 规则命中路径保持低延迟
- 语义增强不会导致系统不可用
- 高风险外发类场景无明显漏拦截
- 关键审计记录可完整回放

## 8. 阶段 4：规模维护性验证

### 8.1 阶段目标

- 验证项目在后续功能扩展和多人维护下是否仍能保持稳定边界

### 8.2 核心任务

- 清理历史接口不一致问题
- 收敛 manager 与 service 层职责
- 建立规则治理机制
- 建立场景文档与测试模板
- 评估是否引入 `Spot` 作为离线增强引擎
- 持续维持“主链自研轻量 RV、现成引擎只作可选增强”的边界

### 8.3 维护性验证重点

- 新增一个办公场景是否只需增加 adapter + rule + rv 模板
- 是否存在过多逻辑继续堆在 `manager.py`
- 规则数量增长后是否仍可解释和可测试
- 初学者是否能在文档指导下新增一个简单场景

### 8.4 交付节点

- 模块边界调整清单
- 规则治理文档
- 新场景接入模板
- 可维护性评估报告

### 8.5 验收标准

- 新增场景的改动范围可控
- 场景规则、语义 schema、RV 模板形成固定模式
- 文档可支持后续继续扩展邮件、日报之外的办公场景

## 9. 全阶段同步要求

所有阶段都必须同步执行以下要求：

- 安全合规同步
  - 不允许为了追求自动化而绕过审批与审计
  - 所有外发类动作默认更严格
- 文档同步
  - 方案、接口、规则、测试用例必须同步更新
- 测试同步
  - 每新增一个场景都要至少补一条规则测试、一条语义测试、一条 RV 测试
- 学习同步
  - 每阶段结束输出一份“学到了什么、哪里还不懂、下一步补什么”的学习记录

## 10. 初学者友好的学习节奏建议

建议按以下顺序学习与开发：

1. 先学当前主链和数据模型
2. 再学结构化输出和 schema 校验
3. 再学简单状态机和有限窗口规则
4. 最后再接触 LTL/LTLf、`Spot` 这类离线增强工具

不建议一开始就：

- 同时学复杂 Agent 编排
- 同时学重型工作流平台
- 同时学完整形式化验证体系
- 直接把重型现成 RV 引擎接入运行主链
