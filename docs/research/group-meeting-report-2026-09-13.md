## 一、系统怎么接进去，决策发生在哪一步

Guard 不改 OpenClaw 源码，只挂两个 Hook：调用前 `before_tool_call` 截住请求，调用后 `after_tool_call` 拿执行结果。OpenClaw 原生审批页是唯一的批准/拒绝入口，Guard 页面只做只读同步、解释和审计，不提供第二个批准按钮；`before_prompt_build` 只写审计，不产生待审批项。Guard 最终只输出三个动作：放行、审批、拦截，交给 OpenClaw 执行。

9 月把这条链路切成两半，解决三个真实问题。一是以前 Guard 页面自己维护一套待审批状态，和 OpenClaw 原生审批形成两个入口，同一个动作会被问两次。二是以前执行前就把动作记进状态窗口，于是"待审批""被拒绝""被阻断"的调用也形成了跨步攻击链证据，窗口被噪声污染。三是以前会话风险分数只升不降，几轮普通操作就能把正常任务顶成极端风险。

现在的规则是：`before_tool_call` 只做预览，用已提交的窗口加上当前候选做一次纯回放，出判定但不写状态；`after_tool_call` 且这次调用确实成功、没被拒绝也没被阻断，才把 trace 和主体权限证据提交进去。**没执行的动作不产生证据**。自动机内部算出的升级在出口统一折叠成"审批"，公开的动作集合不会膨胀。窗口按会话隔离，有长度和 TTL 上限，窗口过期、会话释放或重置会真实降维，不会留着旧状态。

## 二、权限建模：每次工具调用变成一份九维权限档案

旧引擎的根本问题是"工具名 + 语义标签 → 命中规则"。它把工具名当权限，叫"读取"的工具参数里可能藏着删除、外发、读凭据；它不知道 Agent 已经持有什么权限，分不清正常使用和越权扩张；它只看单步，一串各自无害的动作拼起来就漏；它还只盯当前会话，换个会话继续做就查不到。这四点决定了四条设计主线：补权限本体、补最小权限差分、补危险组合、补跨会话主体视角。

权限本体选了 RBAC、ABAC、ReBAC、Capability 的混合模型，因为没有一个单独覆盖 Agent 场景——Agent 既是主体，又会被 Skill 委派。RBAC 提供稳定的角色基线，ABAC 承担时间、敏感度、工作区、收件人域这类动态属性，ReBAC 描述主体—Agent—会话—工具—资源之间的关系，Capability 表示一次性授权和它的来源链路（lineage）。工程上，工具调用不等于权限：`TraceCompiler` 先把工具名和别名解析成规范权限族（`file.read`、`process.execute`、`network.egress`、`secret.read`、`session.token.read` 等），再叠加资源作用域、数据敏感度和主体身份。这样"工具名很普通但参数在删除或外发"就藏不住了。

归一化之后的结果是一份九维权限档案，也就是 Authorization Trace，缺哪一维都会影响处置：

| 维度 | 内容 | 处置影响 |
|---|---|---|
| 主体 | 人 / Agent / Skill / Service，身份是否可信 | 只有可信身份能参与跨会话合并 |
| 执行体 | 哪个 Agent、能力从哪来（agent_id + capability_lineage） | 防止不同 Agent 之间错误继承权限 |
| 操作 | 规范化后的权限族与工具来源 | 解析不出来就是 unknown_tool |
| 资源 | 路径、URL、收件人、文档、表 | 决定是文件、网络还是数据动作 |
| 范围 | workspace / managed_project / outside / external / unknown | unknown 不当宽泛许可 |
| 数据 | public / internal / sensitive / secret | 决定外发是否致命 |
| 上下文 | 内外部去向、业务目的 | 同一操作不同去向处置不同 |
| 覆盖度 | complete / partial / unknown / conflict | 决定能不能自动放行 |
| 来源 | 语义从哪来、可不可信 | 不可信文本不直接变授权 |

**原则只有一条：证据不全就不放行。** 缺主体、缺资源、缺范围、缺去向，一律升级人工审批；`unknown` 和 `conflict` 永远不会变成自动放行。

规则匹配不再等于关键词交集，而是证据比对，结果分四档：完全命中、缺证据、无法确认、冲突，只有"完全命中"能进低风险自动放行。匹配分数（操作动作 0.40、必填字段完整度 0.25、谓词特异性 0.20、来源可信度 0.15）只是解释性证据，不是放行开关——任何 unknown 或 conflict 都挡住 `auto_allow_audit`。这套做法来自 OPA/Rego 和 Cedar 的共同经验：在线策略的稳定性来自规范化请求对象和显式 schema，不是"理解得像不像"；所以"仅发内部域""除 X 外"这类否定和例外，是作为结构化谓词保留的，不靠关键词。

最小权限做成运行时差分，而不是静态审查。系统先算出该 Agent 已持有权限的传递闭包，再和本次请求比：重复申请的标记 redundant、不增加授权；范围从工作区内扩到工作区外触发审批；委托提权必须带证据，没证据就拒。危险组合用超边表达，命中就升级或拦截：

| 组合 | 处置 |
|---|---|
| 读凭据 + 外发 + 外部目标 | 拦截 |
| 读会话令牌 + 外发 + 外部目标 | 拦截 |
| 授予权限 + 导出数据 + 外部收件人 + 敏感数据 | 拦截 |
| 修改认证配置 + 关闭审计 | 审批 |

组合判定是拿"已持有权限 + 本次请求"一起算的，所以单步安全但和历史能力拼起来危险，一样会命中。跨会话部分按主体聚合：权限自动机按 `(主体, Agent, 能力谱系)` 编译，状态持久化，服务重启可恢复；会话 A 读了机密、会话 B 想外发，会被识别成同一主体在做危险组合。审批通过的动作成为该主体的有效能力，只升不降；身份不可信就不参与合并，宁可升级处理。

八个攻击场景现在都有明确处置：

| 攻击 | 改造前 | 改造后 |
|---|---|---|
| 注入后诱导外发 | 部分覆盖 | 来源可信度 + 密钥 + 外发组合，拦截 |
| 只要摘要却带全量权限 | 无法判断 | 闭包 + 差分，只授读取 |
| 重复授权 / 范围扩大 | 无法区分 | redundant / outside 分开处置 |
| 危险组合 | 单步漏 | 超边命中，升级或拦截 |
| 跨会话外发 | 独立窗口漏报 | 主体聚合命中 |
| 否定语义（"仅内部""除 X 外"） | 关键词丢失 | 结构化谓词保留 |
| 工具名伪装 | 只看名字漏 | 参数副作用归一化 |
| 供应链技能越权 | 无能力比对 | 能力声明 vs 运行时差分 |

## 三、PMKB：权限逻辑的物理载体

权限模型是逻辑，必须有一个可版本化、可校验、可回归的载体，否则规则散在代码里，说不清这版改了什么、和上版是否一致。PMKB 1.1.0 现在包含：47 个规范操作（工具名/别名到权限族）、35 条原生规则（含匹配条件、处置、来源、正反例）、47 条 `LEGACY-*` 兼容记录（由旧检测规则自动生成，逐条回放对齐）、29 条最小权限 Trace、9 条危险关系和 29 个回归向量。

结构上它不是一个代码文件，而是一组按职责分层的 JSON 文档：源码根在 `policies/permissions/`，下面分 `schema`、`catalog`、`rules`、`traces`、`relations`、`tests` 六个目录；同一份内容再打包进 `openclaw_guard/policy/data/permissions/`，加载器 `PolicyBundle.load()` 先认源码目录、再认打包镜像，不依赖进程工作目录，两份内容不一致由测试断言拦下。包的形态由 schema 固定：`type` 必须是 `policy-bundle`，顶层 `version` 与五个组件文件各自的 `version` 必须全部相等（当前都是 `1.1.0`），effect 只允许 `auto_allow_audit`、`openclaw_approval`、`block` 三种，`match_status` 只允许 `matched`、`partial`、`unknown`、`conflict` 四种。

内容按"回答什么问题"分成五类。操作目录回答"这个工具在授权语义上是什么"：47 条记录给每个工具名和别名指定一个规范权限族（`file.read`、`network.egress`、`session.token.read` 等），解析不出来的工具落到 `unknown_tool`。规则回答"什么条件下怎么处置"：每条带 `id`、`version`、`effect`、`priority`，`match` 条件（操作族、别名、数量阈值等）、`required_fields`（必须出现的证据维度）、`negative_conditions`（"除 X 外"这类负条件）、`obligations`、`source`、`test_vectors`、`rollback_state`，以及正反例——正反例不是注释，是规则变更后要回放的期望值。Trace 回答"做成这件事最少需要哪些权限"：29 条记录通过 `rule_id` 挂在规则下，列出 `required_permissions`，给最小权限差分当基准。关系回答"哪些权限凑在一起才危险"：9 条记录用 `requires` 把权限族和 `external_target`、`sensitive_data`、`audit.modify` 这类虚拟端点连成超边，再配 `effect` 和回滚状态。向量回答"改完有没有跑偏"：29 条带 `expected_effect`、`rule_id`、`category` 的回归向量。

设计的取舍只有一条：PMKB 是声明式数据，不是判定逻辑。它负责"规则长什么样、来源是谁、改过什么、怎么回滚"，结论仍由评估器连同权限闭包、差分和风险图一起算。记录一加载就冻结，运行期改不了；47 条 `LEGACY-*` 也不是手写的，而是加载时由冻结的旧规则元数据自动生成（`match.operation` 为 `*`），保留原来的匹配条件和处置，只作为迁移与回滚的证据。这样改一条规则不用改代码，回滚也不用改代码，代价是每次加载都要做一遍完整校验和版本比对。

可信性靠四件事保证：加载即校验（重复 ID、未知操作、版本不一致、缺必填字段全部拒绝）、加载后冻结（运行时不可改）、源码目录与打包目录内容一致（测试断言）、每条规则标来源。向量检索只做候选召回，授权结论必须由确定性 schema 和评估器给出，不允许"embedding 当授权依据"。

按权限族看基线处置：工作区内、证据完整、低敏感的目录读取和表读取走 `auto_allow_audit`（放行但留审计）；文档写入、文件写入、数据导出、网络外发、命令执行、凭据读取走审批（敏感导出直接拦截）；会话令牌读取直接拦截；授予权限、修改认证、修改审计走审批。缺主体、缺资源、缺范围、缺去向的请求，状态降级后处置升级，不静默放行。

规则不是凭空写的，主要来自真实事件：Okta 支持事件提炼出会话令牌读取拦截和凭据读取审批；微软 Token Tactics 提炼出认证修改审批和令牌 + 外发组合；Solorigate 提炼出权限授予审批和"授予 + 导出 + 外部 + 敏感"组合；Google/CISA 的 IAM 治理经验支撑最小权限差分和职责分离组合；EchoLeak（CVE-2025-32711）和 Unit 42 的 Agent Session Smuggling 支撑危险组合超边和跨会话聚合。另外修掉一个老误报：`read`/`cat`/`grep`/`ls` 不再因为带路径被判成文件写入。

9 月这里完成收口：`DetectionEngine` 已从生产模块删除，`policy/legacy.py` 只保留冻结的回放元数据；47 条 LEGACY 记录继续作为迁移和回滚证据，逐条离线回放确认效果一致后就能删掉兼容层。同时新增三条原生条件：破坏性命令拦截、特权命令审批、密钥 + 外发拦截。

## 四、自动机编译与运行时验证

PMKB 不是给人看的规则表。知识库加载时由 `PermissionAutomatonCompiler` 一次性编译成运行时监视器：每条规则编译成一个会话监视器，在单个会话内跟踪状态；每条危险组合编译成一个主体监视器，跨会话跟踪能力累积。编译产物带来源标记，每个监视器都能回溯到知识库里哪条规则或组合，审计可以直接回链。职责边界很清楚：PMKB 出权限结论，自动机只负责把结论纳入运行时监视，它自己不下结论，也不重复实现策略引擎。

编译粒度是整体的、一次性的，不是"只编译命中的规则范围"。知识库加载完成后，`PermissionAutomatonCompiler` 把整份冻结的 bundle 全量翻译成监视器规约：每条规则一个会话作用域监视器（当前 82 条 = 35 条原生 + 47 条 `LEGACY-*`），每条带处置效果的危险组合一个主体作用域监视器（当前 9 条，5 条拦截、4 条审批），一次编译产出 91 个规约，每个都带 `source="pmkb"` 和 `source_ids`。命中判定不发生在编译期：每次调用的权威结论由评估器给出，再合成一个 `pmkb.permission` 步骤喂进来，步骤的 props 里带 `pmkb:rule:<规则 ID>` 和 `pmkb:relation:<关系 ID>`，生成的监视器只比对自己的 ID、最终 effect 和 `matched`、`partial` 状态——命中的才出判定，没命中的空转；纯推导关系（`implies`）不落监视器。不按命中裁剪编译，是因为编译描述的是策略本身而不是某一次调用：全量编译让策略保持单一来源、产物稳定可回归、审计能按 ID 回链；按命中裁剪等于让编译产物变成运行时输入的函数，回滚和复现都得跟着调用序列走。运行期真正按作用域裁剪的是实例化：会话监视器按会话隔离，主体监视器按 `(主体, Agent, 能力谱系)` 隔离，而且每次评估都从已提交窗口重建实例，避免过期或被拒的调用把终态留在后面的窗口里。

除了 PMKB 编译出来的规则监视器，运行时还有几类监视器，各自盯的东西不一样：

| 监视器族 | 生成来源 | 状态作用域 | 主要负责什么 |
|---|---|---|---|
| 行为链监视器 | `rv/rv_rules.json` → ChainRule DSL | 会话 | 有序行为链：搜索→删除、敏感读取→外发、批量导出、广播、报告外发等；默认启用，当前 8 个监视器 / 61 条链规则 |
| PMKB 规则监视器 | PMKB `rules` | 会话 | 把单步权限结论（放行 / 审批 / 拦截）纳入会话状态、审计和耗时统计；当前 82 个 |
| PMKB 关系监视器 | PMKB `relations` | 主体 | 跨会话能力累积与危险组合结论的落点；当前 9 个 |
| 基线偏离监视器 | 已确认的正常抽象轨迹训练出的 DFA | 监视器实例 | 偏离正常轨迹的异常信号；默认不加载，只作告警，不能成为放行的依据 |

还有两个不叫监视器、但决定监视器看到什么的组件：滑动窗口负责最近 10 步、TTL 300 秒的行为链，并提供累积计数、序列匹配、实体匹配、时间间隔这些原语；`PrincipalSecurityState` 负责跨会话主体的授权证据，TTL 300 秒、最多 256 个身份键、持久化到 `runtime/rv-state.json`，它记的是"已确认执行过什么"，不是"曾经观察到什么"。分工边界不因为监视器变多而改变：PMKB 出结论，自动机只把结论搬进监视器；行为链和权限链不互相伪造标签，合成出来的权限步骤不带业务标签，不会被行为监视器二次消费；主体监视器只对可信身份建立状态，文本里自称的身份没有跨会话合并资格。

一次调用的完整过程是：拦截 → 语义理解 → 生成九维档案 → 规则匹配 → 最小权限检查 → 危险组合检查 → 自动机验证（会话 + 主体）→ 决策合并 → 执行并审计。整个过程有四条硬约束：会话内看当前行为链（滑动窗口默认 10 步）；跨会话看主体的能力组合，键是 `(主体, Agent, 能力谱系)`，持久化可恢复；只升不降，放行 < 审批 < 拦截，任何环节判定危险，后续环节不得降回放行；每一步都留审计，为什么放行或拦截、命中哪条规则、还缺什么证据，都能回查。

9 月新增的提交边界接在最后一步：前面全部是预览，只有真实执行成功才提交状态。这直接解决了"用审批请求刷风险分"这类噪声，也让攻击链证据只能由真实执行序列构成。

## 五、审批交接：从"什么都问"到"问得少但问得准"

8 月一次真实任务跑了 65 次工具调用，其中要求修改 45 次、升级 10 次、审批 8 次、直接放行 1 次、拦截 1 次。也就是说正常任务几乎每一步都被要求修改或审批，用户体验是"Guard 什么都不让干"；这 65 次里还有 9 次执行失败，其中 5 次是审批说明太长导致审批卡片根本没创建成功——命令越长越容易被拦，这不是安全语义，是交接 bug。

当时判断出两个根因。一是 OpenClaw 自带的只读工具（查会话、查记忆、看目标）没被识别成低风险读取，频繁进审批；会话风险一高，连安全读取也被改写。二是审批卡片的字段长度限制被超长说明撞爆。修复分四步：把原生只读工具显式建模，自动放行并留审计，发消息和跨会话操作不享受这个待遇，参数里出现外部 URL、绝对路径或跨会话目标就退出低风险信任；风险升级只作用于危险调用，安全读取不再被历史高风险拖累；审批标题限 80 字符、说明从 240 放宽到 512 字符，完整依据留在审计详情；超过 6 分钟没回调的审批自动标记超时收拢，不让它一直挂着。

9 月把审批卡片本身重做了。卡片只放"要做什么 / 目标 / 风险"三件事，命令预览默认脱敏——bearer token、`--token` 之类的参数、`key=value` 形式的凭据、URL 里的账号信息（只保留域名）、敏感路径（`.env`、`.git`、`.ssh`、凭据、私钥、`*.pem`、`*.key`）统一遮蔽；完整命令、参数和规则证据留在 Guard 页面，分区折叠。Hook 的响应也不再回显原始 payload，路径、URL、命令、argv 全部清空，完整事件只留在 Guard 内部用于审计和 Dashboard。

同一批工作里加了精确信任 `allow-always`，关键点是**信任的粒度是命令，不是工具**。fingerprint 由工具、完整规范化参数、工作目录和已验证的 agent/principal 一起构成，默认记 30 天，可以在设置页列出并撤销。它只对"确定性解析出的低风险工作区只读命令"开放；破坏性、网络、特权命令，以及指向敏感目标的命令一律不开放；参数没有收敛的未知工具也不行。越权防护包括：指向敏感目标的符号链接、绝对或父级路径、越出工作目录的链接，全部回到单次审批；匿名请求不能建立持久信任；HTTP Hook 会把鉴权 token 换成服务端绑定标识，避免跨安装实例复用授权。配套的前端改动是摘要卡加分区折叠，新增精确授权列表、过期和撤销入口，仍然不提供第二个批准按钮。

## 六、AgentDojo 评测：框架可信，首轮数据作废

评测基础设施是可信的：接了官方 `get_suite()` / `load_attack()` / TaskSuite 评分链路，做无防护、旧引擎、新系统三组对照，并且把"弹审批"和"拦截"分开统计，`deny` 和 `allow-once` 不混算；环境是 agentdojo 0.1.35 加 Python 3.11.15，preflight 通过。

但首轮结果全部作废，三条硬证据：demo 配置里 `max_tool_iters=2`，每集只允许两次工具调用，而任务正常需要 10~30 步，攻击链根本没机会形成；无防护组的攻击成功率也是 0%，说明注入链路没生效（论文级无防护通常在 20~80%），三组全 0% 会让"100% 预防"变成假象；另外 candidate 组先前因为缺 Hook token 返回 401，是重跑之后才出数的。所以首轮的预防率、审批负载、p95 一律不能引用。

重跑的前置条件也明确：放开工具调用次数限制，对齐 AgentDojo 默认的 30 步；先跑无防护基线确认攻击能得手（非 0），再跑三组对比；同时核对任务完成率，不能只看安全指标。9 月的清理把依赖退役检测路径的执行器一并删了，正式重跑需要先补一个新执行器。

## 七、工程收敛与修复

8 月记录的工程债，9 月基本收口：版本号从"代码包 0.3.0 / 文档 v0.7.0-dev / PMKB 1.1.0"三处不一致统一到包 `0.7.0.dev0`、展示 `v0.7.0-dev`、PMKB `1.1.0`；HTTP 入口从 legacy_web 双轨收敛到 FastAPI 单一入口，旧 stdlib 实现移出生产包；规则来源从 DetectionEngine 与 PMKB 并存收敛到 PMKB 单源，旧引擎从生产模块删除。唯一没收口的是未提交文件：从 49 个变成 54 个（多了这轮 Checkpoint 升级），另外 `master` 还有 1 个提交没推。

9 月还修了两个会影响可用性的问题。第一个是临时项目插件路径污染 gateway 配置：测试夹具或短期任务在系统临时目录生成插件包，安装逻辑把该路径写进了用户级 `~/.openclaw/openclaw.json` 的 `plugins.load.paths`，临时目录一删，OpenClaw 启动前就会报 `plugin path not found`，而 Guard 自己的启动流程修不了它（先有鸡后有蛋）。修法是加临时作用域隔离——只有正式项目目录能改用户级配置，位于系统临时目录的插件目录一律跳过写入，项目内配置不受限制；手动安装端点共用同一判定。恢复流程写进了文档：先 `openclaw-guard doctor --project-dir … --json`，再 `openclaw plugins registry --refresh` 和 `openclaw config validate`。第二个是 `--port 0` 端到端冒烟起不来，原因是 Uvicorn 0.52 不再暴露监听端口，出现了"先探测端口再绑定"的竞态；改成预先绑定 socket 再交给 Uvicorn，同时修掉 Playwright 并行浏览器共享服务时的 skill 用例竞态。

清理部分是删掉依赖退役检测路径的 A/B/C 实验、AgentDojo 执行器、绑定测试和过时方案文档，净减 3654 行；`testlab/results/` 和实验原始结果保留为历史证据。

## 九、问题、边界与下一步

还存在的问题，按性质分三类。**第一类是可用性**：审批淹没问题在机制上已经消除，但自动放行边界仍需真实使用反馈校准，误拦率和审批量降幅没有真实流量数据。**第二类是没有可对外的评测数字**：AgentDojo 首轮作废、执行器已清理，效果目前只能讲机制和场景。**第三类是运维与能力边界**：2026-09-15 已将不可达策略改为按工具影响分级（低风险审计放行、高影响阻断），仍需真实 Gateway 观测；ptrace/eBPF 采集器仍是探测桩；基线 DFA 默认不加载；NL2Spec 还是模板匹配，没接 LLM；前端组件级单测仍待补；`.env` 里的真实凭据必须留在本地。

下一步按优先级排：

| 优先级 | 事项 |
|---|---|
| P0 | 提交 54 个未提交文件并推送 `master`（建议拆两个提交：Checkpoint UX、配置隔离） |
| P0 | 启动 Guard 后端、重启 gateway，采集真实 before/after 指标：审批量、误拦率、放行率、schema 错误数、超时数 |
| P0 | 同步文档与 CHANGELOG 的验证数字（494/19 → 498/18） |
| P1 | 补健康检查与熔断告警，给 fail-open 兜底 |
| P1 | 重跑 AgentDojo：先补执行器 → 放开工具调用步数 → 验证无防护基线非 0 → 三组对照并核对完成率 |
| P1 | 删除 `LEGACY-*` 兼容层（逐条回放确认一致后） |
| P2 | 补前端组件测试与 CI 构建门禁 |
| P2 | 做真实流量看板：按规则版本统计命中率、未知率、误报率、高风险召回率 |
| P2 | 采集器落地或移除虚设配置；软著与答辩材料 |

一句话总结：机制已经建齐并完成收敛收口，但整条链路还没经过真实流量检验——可用性靠离线回归撑着、安全性没有有效评测数字、运维兜底缺失，下一步重心从"建机制"转向"验证"。
