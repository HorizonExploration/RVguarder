# M1 认证执行后成功证据

## 本轮完成

- HTTP执行后路由与执行前路由一样，用服务端认证依赖覆盖客户端的 `_hook_auth_verified` 与 `_hook_auth_binding`。
- 对执行前已经认证的动作，执行后必须保持同一认证绑定；已有tool、Agent、session/run上下文不能遗漏或替换。失败回调不会把动作提交成成功。
- 生成的JS从SDK工具结果根字段 `isError === true`产生 `toolResultFailed`。工具参数或结果文字中的同名字段不作为该标记。
- `error`为空但工具结果报错时，动作记为failed，不提交主体或RV成功历史。
- 正常成功回调只提交一个已有 `tool-call-v1` 事件，重复回调仍不能重复提交。来源写入 `provenance.completion_evidence`，不增加调用或效果。

内部旧回放接口允许其原来的非认证调用，但来源明确标记 `legacy_internal_callback`，不升级成认证证明。实际Bearer认证也不能单独证明Agent/session字段的宿主来源；后续授权放行仍需独立验收该作用域。

## 成功不等于内容血缘

成功来源固定记录 `content_lineage_verified=false`、`content_evidence=not_provided`。工具摘要、附件文字、参数中的授权声明、外部返回的hash和Oracle对象关系不能自行改成可信内容证明。

下一步的内容证据必须由受控工具执行器提供，至少绑定有限工具调用的操作、run/call、Agent/任务、命名空间、源/输出内容版本及实际成功状态，并满足：

1. read说明读取范围；部分读取不冒充完整文件快照。
2. copy/打包记录实际源和输出内容，不能只靠参数路径关联；失败或未执行不建边。
3. 变换结果不自动变成公开内容；公开分类仍要求独立可信来源。
4. 证据绑定受控执行器和调用身份，不从 `resultSummary` 解析伪造血缘；不能复用不同任务或资源版本。
5. 在改变RV裁决前解决执行时内容版本或不可变快照问题。后台引用诊断不能作为同步授权证明。

这些条件目前尚未完成，因此M1仍未通过。本轮不改变已有审批/独立block策略。
